# Автономный VPS с 3x-ui

[English documentation](README.md) · [Первоначальная настройка через консоль провайдера](docs/bootstrap-console.ru.md)

Этот репозиторий настраивает **один новый VPS с Ubuntu 24.04**. В начале доступен `root` с паролем. Затем создаётся отдельный пользователь `ops` с входом по SSH-ключу и `sudo` без пароля. После проверки доступа устанавливаются самостоятельная панель 3x-ui, подписка, VLESS/TLS и, по выбору, Hysteria2. Этот VPS является основным контроллером; подключение к нему других серверов выполняется позднее отдельной процедурой.

Плейбуки 3x-ui адаптированы из `vps-fleet-ops`. Сохранены ограничение одним сервером, закреплённая версия установщика с SHA256, локальный bearer API, резервная копия SQLite и вывод без секретов. Инвентарь существующего флота не нужен.

## Что нужно до начала

- На управляющем компьютере: Python 3.10+, `ansible-core`, OpenSSH и `ssh-keygen`. Для первоначального входа Ansible по паролю с `--ask-pass` требуется `sshpass`.
- Новый VPS с Ubuntu 24.04, доступной консолью провайдера, начальным входом `root` по паролю через SSH или эту консоль, публичным IPv4 и достаточными ресурсами для 3x-ui и Nginx.
- Публичное DNS-имя, указывающее на VPS. В фаерволе провайдера должны быть разрешены выбранный SSH-порт, `80/tcp`, TCP-порт VLESS, TCP-порт подписки и, если включена Hysteria2, её UDP-порт. К порту панели допускаются только указанные адреса администраторов.
- Перед развёртыванием проверьте точный тег установщика и SHA256 в `ansible/playbooks/3x-ui-install.yml`. Репозиторий закрепляет `v3.7.0` и не выбирает новую версию автоматически.

Реальные параметры, учётные данные, резервные копии и экспорты не должны попадать в Git. Пароль `root` Ansible запрашивает в терминале; в `.env` он не хранится. До первоначальной настройки проверьте отпечаток SSH-ключа сервера через консоль провайдера и внесите соответствующий публичный ключ сервера в `known_hosts` на управляющем компьютере. Установщик использует `StrictHostKeyChecking=yes` и не принимает неизвестные ключи автоматически.

## Первый запуск: ключ, пользователь, панель

1. Выполните `cp .env.ru.example .env` и заполните `.env`. Английский шаблон — `.env.example`. Порты панели и подписки должны различаться. VLESS на `443/tcp` и Hysteria2 на `443/udp` могут использовать один номер порта. `ENABLE_HYSTERIA=no` отменяет создание её inbound и правило для UDP. Если `CHANGE_SSH_PORT=no`, задайте `SSH_TARGET_PORT` равным `BOOTSTRAP_SSH_PORT`; сохранение SSH на `22` — осознанное исключение из политики исходного флота.
2. Запустите `python3 bin/vps.py plan`. Проверьте план портов, DNS, фаервол провайдера и возможность восстановления через его консоль.
3. Создайте локальный ключ командой `python3 bin/vps.py keygen` либо укажите существующую пару в `SSH_KEY_PATH`. При создании ключа задайте парольную фразу; перед развёртыванием добавьте защищённый ею ключ в `ssh-agent`. Приватный ключ остаётся только на управляющем компьютере.
4. Запустите `python3 bin/vps.py bootstrap --apply`. Ansible запросит начальный пароль `root`. Плейбук создаст пользователя, установит **только публичный ключ**, запишет проверенный файл в `sudoers.d` и проверит новое подключение по ключу с `sudo -n`. До успешной проверки старый способ входа сохраняется. Если вход `root` по SSH запрещён, выполните [первоначальную настройку через консоль провайдера](docs/bootstrap-console.ru.md). Для проверки ручного варианта временно установите `CHANGE_SSH_PORT=no` и оба SSH-порта равными текущему, затем запустите `python3 bin/vps.py verify-access`. Перед следующим шагом верните планируемые значения портов.
5. Запустите `python3 bin/vps.py check-network`, затем `python3 bin/vps.py deploy --apply`. Сначала открываются текущий и новый SSH-порты. После отдельной проверки входа по ключу на новом порту отключаются вход `root` и парольная SSH-аутентификация, а старый порт закрывается. Затем устанавливаются 3x-ui, API-токен, локальный Nginx fallback, сертификат, подписка, VLESS/TLS и выбранная Hysteria2. Завершает процесс проверка состояния без изменений на сервере.
6. После установки и перезагрузки выполняйте `python3 bin/vps.py verify`. Учётные данные панели смотрите **на самом VPS** в `/etc/x-ui/install-result.env` через проверенную учётную запись. Не копируйте их в Git или переписку.

`check-network` показывает план, но на нетронутом сервере не может предсказать все последствия изменения служб, особенно если UFW ещё не установлен. Успешный check mode не доказывает, что порт реально слушается и доступен через фаервол провайдера. Каждый изменяющий плейбук ограничен `--limit standalone`. Установщик передаёт только несекретные параметры во временном файле с правами `0600` и удаляет его после запуска; токены и созданные учётные данные остаются на VPS.

## Проверка подключения клиента

1. Откройте панель администратора только из `PANEL_ALLOWED_CIDRS` или через SSH-туннель. Проверьте сертификат и вход.
2. Проверьте inbound VLESS/TLS на выбранном TCP-порту. Если включена Hysteria2, проверьте её inbound на выбранном UDP-порту. Создайте в панели по одному временному клиенту для каждого выбранного протокола и получите ссылки подключения.
3. Импортируйте ссылки на устройстве во **внешней сети** и проверьте аутентифицированное прокси-соединение для VLESS/TLS и, если включена, Hysteria2. Проверьте доступность IPv4 и совпадение DNS-имени с сертификатом.
4. Откройте адрес подписки, который показывает панель. Убедитесь, что там только нужные клиенты и протоколы, затем обновите подписку на внешнем устройстве. Открытый локальный порт не доказывает работу подписки.
5. Удалите временных клиентов после проверки либо явно передайте их учётные данные администратору. До добавления рабочих клиентов сохраните резервную копию SQLite и сертификатов.

Без настоящего VPS и внешнего клиентского устройства установщик не может провести этот тест автоматически. Он отдельно сообщает о завершении плейбуков и о необходимости приёмочной проверки.

## Восстановление и повторный запуск

Установщик не переустанавливает существующую панель без отдельного решения; создание inbound отказывается от дубликатов. После ошибки или прерывания **сначала** проверьте доступный SSH-порт, `sudo -n`, `sshd -T`, `ssh.socket`, `ufw status`, `systemctl is-active x-ui` и состояние 3x-ui. Лишь после проверки фактического состояния продолжайте с нужного этапа, например `python3 bin/vps.py deploy --apply --from-stage cert`. Доступны этапы `network`, `install`, `token`, `fallback`, `cert`, `subscription`, `vless`, `hysteria`, `verify`.

Если SSH недоступен, войдите через консоль провайдера. Проверьте управляемые файлы в `/etc/ssh/sshd_config.d/` и `/etc/systemd/system/ssh.socket.d/`, выполните `sshd -t`, проверьте UFW и восстановите заведомо рабочий порт перед перезапуском SSH. При ошибке панели сначала изучите резервные копии SQLite на сервере в `/root/`. Не запускайте повторно частично выполненное создание inbound без проверки.

## Подключение других узлов позднее

Эта панель может стать основным контроллером для удалённых узлов 3x-ui. Перед регистрацией узла отдельно спланируйте ограниченный доступ к его панели/API, учётные данные, размещение клиентов и их видимость в подписке. Первый запуск не регистрирует другие VPS и не меняет их.

## Файлы репозитория

- `.env.ru.example` и `.env.example` — шаблоны параметров с русскими и английскими комментариями.
- `bin/vps.py` — локальная проверка параметров и поэтапный запуск.
- `ansible/playbooks/bootstrap.yml`, `network.yml`, `ssh-cutover.yml`, `verify.yml` — первоначальный доступ и настройка системы.
- `ansible/playbooks/3x-ui-*.yml`, `proxy-fallback-nginx.yml`, `ansible/roles/proxy_fallback_nginx/` — установка панели и инбаундов.
